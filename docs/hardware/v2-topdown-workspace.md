| `wrist_roll` anchor | `[0.00018, 0.04323, 0.58437]` |

| `L2` (elbow_flex→wrist_flex) | `0.13500 m` |
| tool offset (wrist_flex→pinch) | `[-0.02700, 0.07280, 0.01055]`, magnitude `0.07836 m` |

Arm B mirrors in y (base `[0, 0.25, 0.35]`), confirmed by `_calibrate('B')`
producing the mirror image of every one of the above to the same precision.

**One measured constant genuinely disagrees with the task brief, and the
disagreement is explained, not just noted.** The brief states the
`wrist_roll` axis as `[0, 0.942, -0.335]`. `ik_geometric._calibrate()`,
which explicitly zeroes ALL FIVE positioning joints (including
`shoulder_lift` and `elbow_flex`) before reading `data.xaxis`, measures
`[0, -1, 0]` instead (arm B: `[0, 1, 0]`) — a materially different vector.
`scripts/v2_probe_kinematics.py`'s own "JOINT AXIS SIGN CHECK" section,
run on bm-ptl, reports `[-0., 0.942, -0.335]` for `wrist_roll` — matching
the brief. The reconciliation: that probe section perturbs each joint from
whatever `data.qpos` already holds at that point in the script, which by
then has been restored to the scene's compiled **"home" keyframe**
(`shoulder_lift=-1.2`, `elbow_flex=-1.6`, not zero — see the probe's own
printed "CURRENT HOME KEYFRAME" section), not the all-zero pose. Since
`wrist_roll`'s axis is rigidly attached downstream of `shoulder_lift` and
`elbow_flex`, its WORLD-frame direction rotates by
`shoulder_lift + elbow_flex` away from its true zero-pose value — at the
home keyframe that is `-1.2 + (-1.6) = -2.8 rad` of accumulated rotation,
easily enough to turn `[0, -1, 0]` into something resembling
`[0, 0.942, -0.335]`. **The brief's `wrist_roll` axis number was measured
at a different (non-zero) reference configuration than its own anchors and
pinch point were** (which independently verify at the true zero pose to 5
decimal places). `ik_geometric.py` measures every constant, axes included,
at the same explicit all-zero reference, so this does not propagate into
the solver — it is caught precisely because the round-trip gate below is
checked against the real compiled model, not against the brief's numbers.

| `shoulder_lift` | `[-1, 0, 0]` | `[0.0000, +0.0136, +0.0289]`, `\|d\|=0.0320` |
| `elbow_flex` | `[-1, 0, 0]` | `[0.0000, +0.0065, +0.0198]`, `\|d\|=0.0208` |
| `wrist_flex` | `[-1, 0, 0]` | `[0.0000, +0.0018, +0.0071]`, `\|d\|=0.0074` |

`ik_geometric.py` does not need any of these numbers hand-encoded: every
rotation it applies uses `mujoco.mj_forward`-measured axis vectors directly
in a general Rodrigues formula (`_rodrigues`), so the correct sign for each
joint is reproduced automatically by construction (see the module's
docstring, "why a sign-convention check is unnecessary here"). This table
is corroborating evidence, not an input the solver depends on.

## 3. Lateral pinch-point offset — how it was handled

Two stacked lateral offsets exist, both handled in closed form (see
`ik_geometric.py`'s module docstring for the full derivation):

1. **Shoulder-plane offset.** The `shoulder_lift`/`elbow_flex`/`wrist_flex`
   sub-chain's own plane sits at local x≈0.01828 m, not on the
   `shoulder_pan` axis itself (local x=0). A naive `atan2(target_y,
   target_x)` for the pan angle is systematically wrong by this amount.
2. **Wrist-roll offset.** The ADR-025 pinch point (midpoint of the fixed
   and moving jaw bodies) is not exactly on the `wrist_roll` rotation axis
   — decomposing the wrist-to-pinch vector into components parallel/
   perpendicular to that axis gives a ~1.6 cm-radius perpendicular
   component, so rolling the wrist traces the pinch point on a small cone
   rather than leaving it fixed.

Both are folded into a single constant `d` (the effective lateral offset,
computed once `wrist_roll`'s angle is fixed from `yaw`), and `shoulder_pan`
is solved via the classic shoulder-offset / "left-arm-right-arm" closed
form: `r_perp = sqrt(dist_to_pan_axis**2 - d**2)`, then `atan2` recovers the
pan angle exactly. This is the "single most likely source of a systematic
error" the task brief flagged — getting it wrong would have shown up
immediately as a large round-trip position error; it did not (see §4).

**A second bug this surfaced and fixed, not just a design note.** An
intermediate version of this module computed the standard "2-link elbow"
trigonometry using a HARDCODED sign (tuned by eye against arm A's own axis
of almost exactly `[-1, 0, 0]`). Arm B's axis measures to almost exactly
`[+1, 0, 0]` — the mirrored asset flips the axis SIGN, not just the base
position — and the hardcoded formula silently used the wrong rotation sense
for arm B specifically: every joint-range check still passed (the solver
still returned five angles), but the returned pose did not reach the
target (round-trip position error ~0.2–0.3 m for arm B, ~0 for arm A).
Caught locally (see §6) before ever reaching bm-ptl, by testing BOTH arms,
not just arm A, against the real compiled model. Fixed by routing the
"absolute link angle" computation through a fully general
axis-aware helper (`_chain_angle`, built on `_signed_angle_about_axis`)
that derives the correct sign from the actual measured axis vector instead
of a hand-typed one. Recorded in DECISIONS.md's ADR-070 entry.

## 7. Validation (d) — comparison against the redesign branch's position-only measurement

Per the task brief: **"Top-down is a strictly stronger constraint so the
reachable set MUST be smaller; report by how much. If it comes out larger,
you have a bug — say so rather than reporting it as a finding."**

**First attempt used the wrong baseline and genuinely failed this check —
reported here rather than hidden.** The redesign branch's workspace
measurement (`git show redesign:docs/hardware/redesign-workspace-
measurement.md`, redesign branch ADR-058 — **not** this branch's ADR-058,
the unrelated Speechmatics ADR; the task brief's own warning about this
numbering collision is accurate and is repeated here deliberately) reports
its **first, N=50000-samples-per-arm "raw cloud"** table as 988–1293
occupied cells per arm per 2 cm z-slice. Comparing THIS module's top-down
counts (1257–1485, §6) against that table makes top-down look **20–35%
LARGER** than position-only — which is logically impossible (top-down
targets are a subset of position-only targets by definition) and, per the
task brief's own instruction, was treated as a bug signal rather than
explained away.

Investigating: the redesign branch's OWN report already diagnoses why that
first table undercounts. Its own "second confound... sampling density"
section re-measured the identical quantity at N=300000 (6×) and found the
occupied-cell count roughly DOUBLED at every slice — direct evidence the
N=50000 table is far from saturated, and the redesign branch's own text
states plainly that the densified numbers, not the N=50000 ones, are the
trustworthy measurement. Switching this comparison to that **N=300000
"raw cloud, densified"** table (the correct, apples-to-apples baseline)
restores the expected result cleanly:

| height (this module) | z | redesign-branch z (densified, N=300000) | arm A: top-down vs position-only | arm B: top-down vs position-only |
|---|---:|---|---|---|
| grasp height | 0.370 | 0.37 (exact) | 1471 vs 2278 — **35.4% smaller** | 1471 vs 2290 — **35.8% smaller** |
| +5cm | 0.420 | 0.41 (nearest; redesign branch has no 0.42 slice) | 1485 vs 2536 — **41.4% smaller** | 1485 vs 2536 — **41.4% smaller** |
| +10cm | 0.470 | 0.47 (exact) | 1257 vs 2679 — **53.1% smaller** | 1257 vs 2674 — **53.0% smaller** |

Top-down reachability is **35–53% of the position-only reachable footprint**
at the three heights tested, shrinking as height increases above the table
(consistent with the top-down pitch constraint becoming harder to satisfy
simultaneously with a large working radius as the arm has to reach further
"over the top"). This module's own workspace measurement has a second
methodological advantage worth stating plainly: because every grid cell is
tested exactly (closed-form `None`/not-`None`), it carries **no Monte Carlo
sampling-density confound at all** — the redesign branch's own report spent
a full extra measurement pass (N=300000, "densification check") specifically
to rule that confound out; this module's numbers do not need that pass.

## 8. A note on ADR-020

This validation script was run authoritatively on bm-ptl (numbers above).
During development, `mujoco` was found to import and run successfully on
this session's laptop environment as well (`python -c "import mujoco"`
succeeds, `TableSettingEnv` loads and steps) — which appears to contradict
ADR-020's premise ("MuJoCo will not import on the laptop... Smart App
Control blocks the unsigned mujoco.dll"). This was used ONLY for fast local
iteration while developing the closed form (catching the arm-B sign bug in
§3 took seconds locally rather than an SSH round trip); every number in
this document is the bm-ptl run's own output, not the laptop's, per the
task's explicit instruction and matching this project's own established
precedent (ADR-047: cross-machine floating-point divergence between bm-ptl
and the laptop). Whether ADR-020 itself needs updating (environment change,
Smart App Control setting, or a difference in which laptop/account this
session runs under) is flagged here for the user's attention and is
explicitly **not** acted on unilaterally — ADR-020 governs where M02
onward's simulation work runs, and changing that classification is outside
this module's scope.
